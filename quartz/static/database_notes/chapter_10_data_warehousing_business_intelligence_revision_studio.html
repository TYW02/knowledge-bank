1.1 & 1.2 Core Purpose & Key Data Dimensions

Application + Time Dimensions

Enterprise Data Warehouse (EDW)

A central repository of integrated data gathered from multiple operational and external sources, specifically engineered for reporting and data analysis in Business Intelligence (BI) systems.

1. Application / Source Dimension

Consolidates heterogeneous operational data across enterprise systems: Sales, Salaries, Operational records, HR, CRM, ERP, Billing, and Supply Chain.

2. Time Dimension (Historical + Current)

Uniquely retains both historical data and current data across extensive multi-year time horizons (whereas operational OLTP databases strictly track short-term current state).

2.2 & 2.3 Ingestion Layers, Challenges & ETL vs. ELT

DataStage & PowerCenter

Staging Layer (ODS)

Temporary storage holding raw data extracted directly from source DBs inside an Operational Data Store (ODS). Raw staging records may be purged after processing.

Integration & Access Layers

Integration Layer: Cleanses and moves staged data into central DW tables.
Access Layer: End-user interface for structured queries, reporting, and multidimensional retrieval.

Industry Tools & ELT Note

Tools: IBM InfoSphere DataStage, Informatica PowerCenter.
ELT (Extract, Load, Transform): Loads raw data first and transforms later—far less popular than ETL in classic EDWs.

Operational Ingestion Challenges

1. Handling massive data volumes (managing ingestion windows & peak traffic spikes).  |  2. Cleansing "dirty data" (missing values, inconsistent formats).  |  3. Maintaining schema and clock synchronization across geo-distributed sources.

3.3 Three Fact Table Types & Star vs. Snowflake Comparison Matrix

Exam Essential

1. Transaction Fact

Records individual atomic business events (e.g., each single customer sales transaction).

2. Snapshot Fact

Captures periodic point-in-time measurements (e.g., month-end inventory or account balance).

3. Accumulating Snapshot Fact

Tracks running cumulative totals across milestones (e.g., monthly cumulative summary totals).

FeatureStar SchemaSnowflake Schema
Dimension StructureDenormalized (single wide table per dimension: Date, Store, Product, Worker, Supplier, Range)Normalized (split into multi-level sub-tables: Day_of_Week/Month/Quarter, Geography, Brand/Category)
JOIN ComplexitySimple (1-level JOIN)Complex (Multi-level nested JOINs)
Read Query PerformanceFast & read-optimizedSlower due to computational overhead of multi-table JOINs
Storage EfficiencyHigher attribute redundancy / uses more disk spaceMinimal redundancy / saves storage space (1NF/2NF/3NF)
Data IntegrityNot strictly enforced at schema level (requires ETL controls)Formally enforced via normalized foreign keys

Core Distinction: DBMS (OLTP Tuned) vs. Data Warehouse (OLAP Tuned)

DBMS (OLTP): Tuned for fast row access, precise indexing, concurrency control, and recovery — used to run a business.
Data Warehouse (OLAP): Tuned for complex multi-table aggregations, multidimensional views, and consolidation — used to optimize a business.
