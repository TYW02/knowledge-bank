Software Engineering Design Fundamentals & Levels

Software design bridges stakeholder requirements ("what") and physical implementation ("how") through iterative architectural, detailed, and construction models.

W8-1-2 Fundamentals

1.1 Formal Definition & Product Development Importance

Dual Definition

Software Design as a PROCESS

The activity of identifying, evaluating, validating, and specifying the architectural, detailed, and construction models required to build software that meets functional and non-functional requirements.

Software Design as a PRODUCT / RESULT

The concrete set of design models, architectural blueprints, and specifications produced by the design process to guide construction, testing, and maintenance.

6 Reasons Why Software Design is Critical (Product Development Perspective):

1. Foundation for Lifecycle

Forms the mandatory foundation for Construction, Testing, and Maintenance phases.

2. Requirements Mapping

Translates abstract requirements into conceptual structural and behavioral models.

3. Early Component ID

Identifies major structural components and their interaction interfaces before coding.

4. Birthplace of Quality

Provides mechanisms to evaluate quality attributes (usability, maintainability, performance) early.

5. Reusability

Design patterns and modular solutions can be reused across multiple software projects.

6. Minimizing Volatility

Absorbs requirements volatility early, minimizing costly schedule and budget overruns.

Design Rules

3. Core Modular Design Principles

Must-Know Definitions

3.1 Modularization

Continuous decomposition of a software system until fine-grained components are created. Prevents ad-hoc decomposition (which yields incoherent, unmaintainable systems). Guided by Abstraction & Encapsulation.

3.2 Abstraction

Focusing on essential characteristics of entities within their active context while deferring unnecessary details (e.g., modeling a manager component before deciding its exact classes).

3.3 Encapsulation

Hiding internal structure, data, and implementation details from external entities—exposing functionality exclusively through well-defined public interfaces.

3.5 Separation of Interface and Implementation

Specifying a public interface (visible to clients) completely separate from how the component is realized internally. Allows internal implementations to be upgraded or swapped without breaking external client components.

3.6 Completeness vs. Sufficiency

  • Completeness ("No Less"): Measures how well designed units provide all required services to achieve their intended purpose.
  • Sufficiency ("No More"): Measures how well designed units provide only the services sufficient to achieve their intended purpose (no bloat).

4.3 McConnell's 5 Levels of Design

Code Complete
Level 1: Software System (Top-level boundary)
Level 2: Division into Subsystems / Packages ← Components!
Level 3: Division into Classes within Packages
Level 4: Division into Data & Routines within Classes
Level 5: Internal Routine Design (Method algorithms)

Encapsulation Loop: Engineers encapsulate classes identified at Level 3 into higher-level Components (Level 2) to manage complex architectures.
