Execution-Based Evaluation

1.1 Black-Box vs. White-Box Testing Comparison

Complementary Paradigms

Black-Box Testing (Functional / Specification-Based)

Treats the software under test as an opaque "black box" with no access to internal source code. Evaluates external inputs and outputs strictly against documented requirements.

Blind Spot: Cannot detect internal implementation errors or extra uncalled code paths (e.g., hidden backdoors or dead logic).

White-Box Testing (Clear / Glass / Open-Box / Structural)

Requires full access to source code. Also called Clear, Glass, Open-Box, Structural, or Logic-Driven Testing. Designs tests from internal control flow and statement logic.

Blind Spot: Cannot detect missing requirements or unimplemented execution paths that were never coded in the first place.

Primary Focus System specifications, functional requirements, inputs, and outputs Internal source code, control flow structures, and statement logic
Code Visibility No access to source code (treats system as an opaque "black box") Full access to source code (Clear, Glass, or Open-Box Testing)

Equivalence Partitioning (EP) Rules

Divides input domain into Valid and Invalid partitions. Only 1 random representative value per partition is needed (minimal set covering the domain): 30 (Invalid < 50), 60 (Valid 50–90), 100 (Invalid > 90).

Boundary Value Analysis (BVA) Rules

Errors occur disproportionately at edges due to operator bugs (e.g., < instead of <=). Tests values at and immediately adjacent to boundaries: Lower (49, 50, 51) and Upper (89, 90, 91).

3.1 White-Box Principles & Test Specification Hierarchy

Foundational Concepts

Necessary Condition Principle

"Executing a faulty statement is a necessary condition for revealing a fault." A defect in code can only be uncovered if test execution forces the processor through the faulty line.

Exhaustive Testing Limitation

Exhaustive testing of all possible input combinations and paths is practically impossible. White-box testing provides the strongest structural guarantees at minimal effort/cost.

1. Test Requirement

What structural element we want to cover (e.g., "all executable statements" or "all decision branches").

2. Test Specification

Logical constraints on inputs required to execute a specific code path (e.g., result >= 500).

3. Test Case

Concrete input values applied based on test specifications, paired with expected output values (e.g., income=1000, expenses=200).

Cyclomatic Complexity & Basis Path Testing Lab

Compute Cyclomatic Complexity M = E - N + 2P, calculate Branch Coverage %, and derive all 4 linearly independent basis paths on the 12-node lecture graph.

M = E - N + 2P

4.1 Cyclomatic Complexity (M or V(G)) & Branch Coverage Calculator

Quantitative Structural Metrics
M = E − N + 2P

E = Edges, N = Nodes, P = Connected components (P = 1 for a single module). Establishes the strict upper bound on linearly independent basis paths.

Branch Cov (%) = (Branches Tested / Total Branches) × 100

Achieving 100% Branch Coverage requires executing both True and False outcomes of every decision node.

M = 14 - 12 + 2(1) = 4 Basis Paths

4.2 Interactive 12-Node Basis Path Derivation Lab (N=12, E=14, P=1 ⇒ M=4)

3-Step Derivation Algorithm

3-Step Algorithm: (1) Establish a baseline path traversing as many decisions as possible → (2) Backtrack to a decision node and flip its outcome → (3) Repeat until all M = 4 linearly independent basis paths are derived (guaranteeing 100% Statement & 100% Branch Coverage).

White-Box Trade-Offs & UAT vs. System Testing

Evaluate the engineering pros and cons of White-Box Testing and distinguish technical System Testing from business-focused User Acceptance Testing (UAT).

Quality & Release Validation

4.1 Advantages & Disadvantages of White-Box Testing

Engineering Trade-Offs

Advantages of White-Box Testing

  • Deep Error Detection: Identifies hidden logic bugs and side effects in internal code.
  • Code Optimization: Helps remove dead code or redundant execution blocks, improving performance.
  • Loop & Path Thoroughness: Systematically evaluates internal loops, conditions, and paths.
  • High Rigor: Provides higher structural thoroughness compared to black-box testing alone.

Disadvantages of White-Box Testing

  • High Technical Cost: Requires testers with deep programming expertise.
  • Impracticality of 100% Path Coverage: Complete path coverage is unfeasible for large applications; defects may still be missed.
  • Maintenance Overhead: Changes in internal implementation details require re-developing test cases even if external functionality is unchanged.

4.2 User Acceptance Testing (UAT) vs. System Testing

Pre-Deployment Comparison
Feature System Testing User Acceptance Testing (UAT)
Primary Goal Verify that system operates without crashing and fulfills SRS specs Confirm that system satisfies business needs and end-user workflows
