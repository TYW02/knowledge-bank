1.1 Five Essential Functions of SCM & The Parachute Scenario

Why SCM Matters

Software Configuration Management (SCM) is a systematic set of engineering activities designed to manage change throughout the SDLC via five essential functions:

1. Identifying work products that are likely to change.

2. Establishing relationships among these work products.

3. Defining mechanisms for managing different versions of work products.

4. Controlling changes imposed on the system.

5. Auditing and reporting on the changes made.

1.2 The Four Core SCM Pillars

1. Change Control

Tracking change requests, analyzing costs/benefits, approving worthwhile changes, and recording altered components.

2. Version Management

Keeping track of multiple CI versions, resolving merge conflicts, and preventing developer interference in shared environments.

3. System Building

Assembling program components, external libraries, configuration files, and data structures into an executable system.

4. Release Management

Preparing approved builds for external customer release, tracking release histories, and coordinating updates or hotfixes.

2. Configuration Item (CI) Taxonomy & Versioning Graph

Versions vs. Revisions vs. Variants

Documentation & Specs

Requirements Specification (SRS), Architecture Design Documents, Software Wikis, and README.md files.

Source & Configuration

Implementation source code, build scripts, dependency manifests, and .gitignore files.

Verification Artifacts

Test suites, automated test scripts, test data, and integration specifications.

Version

An instance of a Configuration Item at a specific point in its development that differs in form, structure, or behavior from instances at other points.

Revision

A version linked to a preceding version via a revision-of relationship and ordered sequentially in time (v1.2 → v1.3 → v1.4). Revisions supersede earlier versions.

Variant

Functionally equivalent versions of a CI that coexist simultaneously tailored for different OS, hardware, compilers, or customer settings (e.g., Android vs. iOS mobile module).

4.1 Core Version Management Terminology

6 Foundational Terms

1. Workspace

An isolated private directory where a developer edits, builds, and tests code without affecting teammates.

2. Check-Out

Operation of copying configuration items from the central repository into a local workspace.

3. Check-In (Commit)

Operation of copying modified items from a local workspace back into the repository.

4. Branching

Creating an independent line of development from an existing version, allowing parallel feature work.

5. Merging

Combining concurrent changes made on separate branches into a unified target branch.

6. Conflict Resolution

Identifying and resolving overlapping, contradictory edits made by different developers to the same file.

6. System Building, Major/Minor Releases & Hotfix Workflow

Build Reproducibility

System Building & Reproducibility

Compiling source code, linking libraries/data files, and packaging environment settings. Build reproducibility ensures any machine builds an identical executable from declared dependencies.

Major vs. Minor Releases

Major Release (v1.0 → v2.0): Delivers significant new functionality & architectural shifts.
Minor Release (v2.0 → v2.1): Bug fixes, security patches & minor enhancements.

Master Branch & Hotfix Workflow

When a production bug occurs on Master, create a Hotfix branch from Master, fix and verify the patch, and merge back into both Master and active development branches.

Why Maintenance Dominates (10–20+ Years)

Good software is maintained for 10, 20, or more years; bad software is discarded. Because post-delivery maintenance accounts for 67%–75% of total cost, long-term maintainability is paramount.

10.3 Cost-Reduction Leverage Comparison

  • A 10% reduction in coding cost (5% share) yields at most a 2% reduction in total lifecycle costs.
  • A 10% reduction in post-delivery maintenance cost (67% share) yields a 6% to 7% reduction in total lifecycle costs!

9. Four Categories of Software Maintenance & Slide Exercises

Corrective (~20%) vs Enhancement (~80%)

1. Corrective (~20%)

Reactive fixes to repair logical errors, runtime exceptions, crashes, or unperformed functions reported post-release.

2. Adaptive (~20%)

Modifying software to adapt to environmental shifts: new OS, compilers, hardware, or government regulations & standards.

3. Perfective (~60%)

Proactive enhancements to improve quality, optimize speed, add new user-requested features, or reduce code complexity.

4. Preventive

Proactively detecting and fixing latent faults or structural weaknesses before production failures occur (e.g., defensive handlers, backups).

Slide Exercise 1

Scenario: A company modifies existing software to comply with new government regulations or industry standards.

✓ Adaptive Maintenance (adapting to external regulatory/environmental changes).

Slide Exercise 2

Scenario: An e-commerce business adds a new product review feature allowing customers to leave star ratings and comments.

✓ Perfective Maintenance (enhancing functionality and adding new user-requested features).

11. Software Refactoring & Interactive 6-Step Refactoring Cycle

Behavior-Preserving
"Refactoring is a change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior." — Martin Fowler (2000)

Refactoring IS:

  • Rearranging internal code structure in small steps.
  • Preserving exact external program semantics.
  • Improving code readability, cohesion, and maintainability (catalogs: sourcemaking.com, refactoring.guru).

Refactoring IS NOT:

  • Adding new user-facing features or functionality.
  • Fixing bugs or debugging operational faults.
  • Rewriting code from scratch without safety tests.

7 & 12. SCM and Maintenance in AI-Assisted Development

Human Accountability

Two Core AI Engineering Principles

1. AI accelerates changes; SCM preserves control.

2. AI contributes code; human software engineers remain accountable for quality, security, risk, and maintenance costs.

Trap: Semantic Non-Conflict Breaks

An AI assistant renames an API parameter from id to user_id in the backend while frontend consumer code still passes id. Git reports zero textual merge conflict, yet runtime functionality breaks! Always version .prompt files, create pre-AI checkpoints, and run full test suites.

Implementing features by hand Understanding requirements and weighing architectural trade-offs

Maintaining code alone Reading legacy code and owning quality, risk, and cost
